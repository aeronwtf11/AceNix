## Confirmed fixes

- Service discovery isolates thrown option values and avoids forcing hidden
  compatibility aliases. Regression testing also exposed an obsolete FRP alias
  that calls `abort`, which native `tryEval` cannot catch. Such names remain
  explicitly unavailable instead of being falsely reported disabled.
- Generation listing reads Nix's native links without a profile write lock.
  Running, booted, profile-default and next-boot systems remain distinct.
- Unreadable regular auxiliary files retain metadata in the conflict snapshot
  but are omitted from the candidate with warnings. Actual unreadable imports
  still fail; inaccessible directories still fail; source/ownership protections
  remain enforced.
- Doctor treats missing source write access as a warning. Evaluation failures,
  conflicts, missing tools and interrupted journals remain failures.
- Human output now has command-specific summaries, tables, readable errors,
  explicit staging semantics, real transaction progress and optional file diffs.
  JSON remains complete; quiet mode suppresses progress; verbose diagnostics,
  `NO_COLOR`, terminal detection and ASCII output remain available.
  Interactive confirmation prompts use stderr so JSON stdout stays clean, and
  end-of-input cancels safely instead of exposing a Python traceback.
- Changed sensitive values retain an explicit change flag after redaction, so
  the preview does not accidentally describe them as unchanged. Modern desktop
  managers are included in high-impact checks. Explicit authorization is retained
  for sensitive settings even when sources match: apply can still change runtime
  and the next-boot system.

## Limits retained

Read-only previews do not grant write access for activation. Local path flakes
need readable source files for Nix's own source fetch. Unavailable hidden service
aliases should be inspected through their current canonical option. Reboot
advice is an inference from changed boot/hardware/hostname options, not a proof
that every possible native module can activate without rebooting. Source syntax,
package ownership, supported bootloader metadata and ARM build limits are
documented in [IMPLEMENTATION.md](IMPLEMENTATION.md).

No live NixOS configuration was edited or activated. Exactly three optional
`TODO(USER)` exercises remain untouched in `acenix/presentation.py`.

## Follow-up: explicit rule paths and requested packages

Additional investigation after the `config.ace` rename confirmed two package
workflow bugs. These findings do not establish the cause of a later installation
report without that report's command output.

- A missing explicit `--rules` file was previously treated as an empty document.
  A typo, or selecting `config.ace` before the existing `config.sys` had been
  migrated, could therefore produce an empty preview and apply the current
  native configuration without the intended package requests. `preview`,
  `apply`, and `get` without an option now reject that missing explicit
  file. Staging commands can still create a new document intentionally. An absent
  default remains valid for a new installation and is identified as
  `(not created; no saved requests)`.
  Native `status` inspection and `get OPTION` remain available for diagnosis
  even when an unused explicitly selected rule document does not exist.
- Candidate verification previously checked new package additions but did not
  verify every positively requested package already present in the original
  configuration. A staged service or option change could change a conditional
  native package definition and drop such a package from the candidate. The
  candidate now checks those requests as well; it cannot report successful
  verification while a requested package is absent. Package removal ownership
  checks and other native definitions remain enforced.

Preview and apply now display the selected rule document so an administrator
can compare it with the file used during staging. User and root defaults remain
separate; AceNix does not automatically import another account's rules, history,
or package-ownership state.

For an existing installation, use the filename that actually exists when passing
`--rules`. Read-only commands continue reading a legacy default `config.sys`
without renaming it. A subsequent default staging write creates `config.ace`
and preserves the original file; an explicit `--rules` selection continues to
use that exact path. After migration, select the new existing path consistently
for preview and apply, with private state owned by the administrator performing
the operation. Merely changing a command's filename is not a migration.

## Follow-up: ordinary staging and sudo administration (2026-10-28)

The explicit `--rules` workaround above is no longer needed for the standard
workflow: `acenix install sl`, `sudo acenix preview`, `sudo acenix apply`.
Validated sudo caller metadata selects the caller's existing, owned rule
document across staging, preview and apply. Without an existing caller document,
sudo-first workflows retain root's defaults. Explicit locations remain available.

Administrator state stays private under root's account; user-owned history and
ownership records are never copied into it. Legacy migration sets the source
owner on the temporary file before publication, so later user staging remains
writable. The README describes this workflow and its advanced overrides.
